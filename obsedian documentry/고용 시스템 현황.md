## 점검 기준

이 문서는 2026-08-21 기준 코드와 JSON 데이터를 바탕으로 인종집단, 연령대, 직업, 건물 노동자와 건설 노동력의 구현 상태를 정리한다.

현재 결론은 다음과 같다.

> 건물별 노동자 수와 생산 배율은 존재하지만, 노동자를 특정 인종집단에서 선발하고 취업·실업 상태를 관리하는 고용 시스템은 아직 구현되지 않았다.

현재 건물은 초기 데이터로 지정된 `currentWorkers`를 이용해 상품을 생산할 수 있다. 그러나 신규 고용이 정상적으로 발생하기 어렵고, Province의 고용 인구와 인종집단별 노동 상태도 실제 건물 노동자 수와 연결되어 있지 않다.

## 현재 인구 데이터 구조

Province는 `provinceEthnicPops`에 지역의 인구 집단을 보관한다.

```text
Province
  └─ List<ProvinceEthnicPop>
       ├─ EthnicGroup
       │    ├─ SpeciesSpec
       │    └─ Culture
       ├─ population
       ├─ ageGroups
       ├─ property
       └─ livingStandard
```

### `EthnicGroup`

`EthnicGroup`은 종족과 문화의 조합을 나타낸다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `species` | `SpeciesSpec` | 종족 기본 정보 |
| `culture` | `Culture` | 문화 정보 |
| `provincePops` | `List<ProvinceEthnicPop>` | 이 집단에 속한 지역별 인구 |
| `Population` | `long` | `provincePops` 인구 합계 |

설계상 한 국가의 같은 종족·문화 조합을 하나의 `EthnicGroup`으로 묶을 수 있다. 그러나 현재 Province 로더는 각 Pop을 읽을 때마다 새로운 `EthnicGroup`을 만들며, 이를 `Nation.ethnicGroups`나 `EthnicGroup.provincePops`에 등록하지 않는다.

따라서 현재 다음 값은 실질적으로 구성되지 않는다.

- 국가 단위 인종집단 목록
- 동일 인종집단의 Province 간 연결
- `EthnicGroup.Population`의 정상적인 합계

### `ProvinceEthnicPop`

`ProvinceEthnicPop`은 한 Province 안의 종족·문화 조합별 인구를 나타낸다.

현재 보유 정보:

- Province 참조
- `EthnicGroup` 참조
- 총인구
- 배당금
- 자산
- 생활수준
- 연령대별 인구

현재 보유하지 않는 정보:

- 노동 가능 인구
- 취업자와 실업자 수
- 직업별 종사자 수
- 건물별 배치 인원
- 임금과 노동소득
- 문해력과 직업 자격
- 고용 선호도와 차별 규칙

## 연령대와 노동 가능 인구

`ProvinceEthnicPop`은 JSON의 인구 배열을 다음 네 연령대로 변환한다.

| 배열 위치 | 연령대 이름 | 현재 용도 |
| --- | --- | --- |
| `population[0]` | `Childhood` | 표시용 인구 데이터 |
| `population[1]` | `Young Adulthood` | 표시용 인구 데이터 |
| `population[2]` | `Middle Age` | 표시용 인구 데이터 |
| `population[3]` | `Older Adulthood` | 표시용 인구 데이터 |

현재 고용 가능 여부는 연령대를 사용하지 않는다. 건물은 Province의 전체 인구가 고용 인구보다 많은지만 확인한다.

```csharp
province.population > province.hiredPopulation
```

따라서 현재 코드에서는 유년기와 노년기도 노동 가능한 인구로 취급된다.

예를 들어 `Provinces.json`의 일부 Province는 모든 인구가 `Childhood`에 들어 있고 나머지 연령대는 0이다. 그럼에도 건물의 고용 가능 검사에서는 해당 인구 전체를 노동 공급으로 계산한다.

### 연령대 갱신 문제

`ProvinceEthnicPop.PopulationGrowth()`는 총인구인 `population`만 성장률만큼 증가시킨다. 각 `AgeGroup.agepopulation`은 함께 갱신되지 않는다.

따라서 연령대 데이터를 고용 시스템에 사용하려면 다음 갱신이 먼저 필요하다.

- 출생 인구를 `Childhood`에 추가
- 시간이 지나면 다음 연령대로 이동
- 연령대별 사망 처리
- 연령대 합계와 `ProvinceEthnicPop.population` 동기화

## 직업 데이터

`JobType`은 다음 필드를 가진다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `name` | `string` | 직업 이름 |
| `literacyNeeded` | `bool` | 문해력 필요 여부 |
| `salary` | `int` | 급여 |

`GlobalVariables.LoadJobTypes()`는 `JobTypes.json`을 읽어 `GlobalVariables.JOB_TYPE`에 직업을 등록한다.

현재 `JobTypes.json`에는 다음 직업 하나만 있다.

```text
peasant
  literacyNeeded: true
  salary: 0
```

직업 데이터는 로드 이후 건물이나 `ProvinceEthnicPop`에서 참조되지 않는다. `Building.GetWorkers()`의 주석은 직업별 노동자 조회를 설명하지만 실제 메서드는 매개변수 없이 `currentWorkers` 전체를 반환한다.

즉 현재는 다음 기능이 없다.

- 건물 타입별 요구 직업
- 직업 자격 검사
- 직업별 노동자 배치
- 급여 지급
- 노동소득의 Pop 자산 반영
- 이직과 실직

## 건물의 노동자 모델

### 노동자 수와 고용 용량

일반 건물은 다음 노동 관련 값을 가진다.

| 값 | 위치 | 의미 |
| --- | --- | --- |
| `workerNeeded` | `BuildingType` | 건물 1레벨을 완전히 가동하는 데 필요한 노동자 수 |
| `level` | `Building` | 건물 레벨 |
| `currentWorkers` | `Building` | 현재 건물에 배치된 노동자 수 |

현재 최대 고용량은 다음 식으로 계산된다.

```text
최대 고용량 = level × workerNeeded
```

`BuildingTypes.json`에서 WheatField와 LogField는 레벨당 노동자 100명이 필요하다.

초기 건물의 `currentWorkers`는 `Provinces.json`의 `workerScale`로 설정된다.

```text
초기 노동자 수 = workerNeeded × workerScale
```

`workerScale`은 건물 레벨과 별도로 적용된다. 따라서 데이터가 잘못 설정되면 레벨 기준 최대 고용량보다 많은 초기 노동자가 들어갈 수 있다.

### 현재 생산 흐름

매주 `GameManager.ProcessWeeklyEvents()`가 각 Province의 `ProduceGoodsWeekly()`를 호출한다.

```text
GameManager.ProcessWeeklyEvents()
  ↓
Province.ProduceGoodsWeekly()
  ↓
BaseProduction()
  ↓
BuildingProduction()
  ↓
Building.ProduceItem()
```

`Building.ProduceItem()`의 생산 배율은 다음과 같다.

```text
생산 배율 = currentWorkers ÷ workerNeeded
```

현재 식에는 건물 레벨이 직접 포함되지 않는다. 다만 건물의 최대 고용량은 레벨에 따라 증가하므로 여러 레벨의 노동자가 들어가면 생산 배율도 함께 증가한다.

이 생산 흐름은 인종집단이나 직업과 무관하게 `currentWorkers`라는 단일 숫자만 사용한다.

## 신규 고용 흐름

`Building.HireWorkers()`는 고용 조건을 만족하면 한 번에 최대 50명을 추가한다.

```text
HireWorkers()
  ↓
IsNewWorkerAvailable()
  ↓
min(남은 건물 고용량, 50명) 추가
```

고용 조건은 다음과 같다.

1. 건물 자금 `balance`가 0보다 커야 한다.
2. 이전 수입 `previousGain`이 0보다 커야 한다.
3. 현재 노동자가 `level × workerNeeded`보다 적어야 한다.
4. Province 전체 인구가 `hiredPopulation`보다 많아야 한다.

### 신규 고용이 사실상 중단되는 조건

`previousGain`은 기본값이 0이다. 현재 프로젝트에서는 이 값을 실제 건물 수입으로 갱신하는 코드가 없다.

따라서 초기 데이터로 `currentWorkers`가 들어 있는 건물은 생산할 수 있지만, `HireWorkers()`를 통한 신규 고용은 `previousGain > 0` 조건에서 실패한다.

또한 `HireWorkers()`는 모든 건물에 매주 자동 호출되지 않는다. 현재 확인되는 호출 경로는 산업 보조금을 지급한 직후의 `GovernmentBudget.ApplyIndustrySubsidy()`뿐이다.

결과적으로 산업 보조금을 주더라도 `previousGain`이 0이면 노동자는 증가하지 않는다.

## `hiredPopulation` 연결 상태

`Province`에는 지역의 고용된 인구를 나타내는 `hiredPopulation`이 있다.

그러나 현재 다음 처리가 없다.

- 초기 건물의 `currentWorkers` 합계를 `hiredPopulation`에 반영
- `HireWorkers()` 성공 시 `hiredPopulation` 증가
- 해고나 건물 폐쇄 시 `hiredPopulation` 감소
- 특수 건물 노동자를 `hiredPopulation`에 반영
- 인종집단별 고용 합계와 대조

따라서 `hiredPopulation`은 기본값 0에서 바뀌지 않는다.

이로 인해 다음 문제가 발생한다.

### 실업자 UI가 전체 인구를 표시

건설 Province 선택 UI는 실업자 수를 다음과 같이 표시한다.

```text
표시 실업자 = province.population - province.hiredPopulation
```

`hiredPopulation`이 0이므로 초기 건물에 노동자가 있어도 전체 인구가 실업자로 표시된다.

### 동일 인구의 중복 고용 가능

각 건물은 Province에 남은 노동자가 있는지를 동일한 `hiredPopulation`으로 검사한다. 이 값이 증가하지 않으므로 여러 건물이 같은 인구를 반복해서 고용할 수 있다.

### 초기 노동자와 Province 고용 통계 불일치

`Provinces.json`의 `workerScale`로 초기화된 `currentWorkers`는 실제 생산에 사용되지만 Province의 고용 통계에는 포함되지 않는다.

## 특수 건물의 인구 배정

`Province.AllocateSpecialBuildingPopulation()`은 우선순위에 따라 특수 건물에 인구를 배정한다.

```text
사용 가능 인구 = province.population - province.hiredPopulation
```

Town 이외의 특수 건물에 먼저 인구를 채우고, 남은 인구를 Town에 배정한다.

이 로직도 다음 정보를 사용하지 않는다.

- 인종집단
- 연령대
- 직업
- 문해력
- 기존 일반 건물의 `currentWorkers`

특수 건물에 배정한 인구도 `hiredPopulation`에 더하지 않는다. 따라서 일반 건물과 특수 건물이 동일한 인구를 동시에 사용하는 상태가 가능하다.

또한 `UpdatePopulation()`이 호출될 때 특수 건물 인구는 다시 배정되지만, 일반 건물 고용과의 일관성을 검증하지 않는다.

## 인종집단별 고용 상태

현재 고용 로직은 `ProvinceEthnicPop`을 순회하지 않는다.

두 개 이상의 인종집단이 있는 Province에서도 건물은 `currentWorkers` 총합만 가진다. 따라서 다음 질문에 코드로 답할 수 없다.

- 어떤 인종집단이 어느 건물에서 일하는가?
- 각 인종집단의 취업률과 실업률은 얼마인가?
- 노동자가 어느 연령대에서 선발되었는가?
- 직업과 문해력 요구를 누가 충족하는가?
- 급여가 어느 인종집단의 자산에 들어가는가?
- 특정 인종집단이 이주하면 어느 건물의 노동자가 줄어드는가?

즉 현재 `currentWorkers`는 실제 인구 객체와 연결되지 않은 집계 숫자이다.

## 건설 노동력과 고용의 관계

[[Nation]]은 `nationManhour`로 한 주에 사용할 수 있는 건설 노동력을 관리한다.

현재 `CalculateManhour()`는 다음 고정값만 사용한다.

```text
nationManhour = GlobalVariables.minimumNationManHour
```

코드에는 건설 회사의 노동력을 반영한다는 TODO가 있지만 다음 값은 아직 건설 노동력에 포함되지 않는다.

- 건설 회사의 `currentWorkers`
- Province의 노동 가능 인구
- 인종집단별 취업자와 실업자
- 직업별 건설 노동자
- 임금과 건설 예산

따라서 현재 일반 건물 고용과 국가 건설 진행은 서로 독립된 시스템이다.

## 구현 시 먼저 결정할 사항

### 노동 가능 연령

어떤 연령대를 노동 가능 인구로 볼지 결정해야 한다.

가장 단순한 초기 규칙은 다음과 같다.

```text
노동 가능 인구 = Young Adulthood + Middle Age
```

게임 설계에 따라 Older Adulthood의 일부를 포함하거나 종족별 노동 가능 연령을 다르게 설정할 수 있다. 다만 첫 구현에서는 공통 규칙 하나로 시작하는 편이 데이터와 테스트를 단순하게 유지할 수 있다.

### 고용 상태의 기준 객체

`Province.hiredPopulation`을 직접 수정하는 방식보다 `ProvinceEthnicPop`이 자신의 고용 상태를 보유하고 Province가 이를 합산하는 구조가 일관성을 유지하기 쉽다.

예시 구조:

```text
ProvinceEthnicPop
  ├─ EmployablePopulation
  ├─ EmployedPopulation
  ├─ UnemployedPopulation
  └─ 직업 또는 건물별 고용 내역

Province.hiredPopulation
  └─ 모든 ProvinceEthnicPop.EmployedPopulation의 합계
```

이 구조에서는 총계가 개별 Pop의 상태와 분리되어 어긋나는 문제를 줄일 수 있다.

### 건물의 노동자 표현

`Building.currentWorkers`를 완전히 제거할 필요는 없다. 성능과 UI 표시를 위한 합계로 유지하되, 실제 원본은 인종집단별 고용 내역으로 두는 방식이 가능하다.

```text
Building
  ├─ workerAssignments[ProvinceEthnicPop 또는 Pop ID] = 인원
  └─ currentWorkers = workerAssignments 합계
```

Pop 객체를 Dictionary 키로 직접 사용하면 저장과 불러오기가 어려울 수 있으므로 안정적인 Pop ID를 도입하는 방안도 함께 검토해야 한다.

## 권장 구현 순서

1. 노동 가능 연령 규칙과 `EmployablePopulation` 계산을 추가한다.
2. `ProvinceEthnicPop`에 취업자·실업자 상태를 추가한다.
3. `Province.hiredPopulation`을 Pop 고용 합계로 계산하도록 변경한다.
4. 초기 `currentWorkers`를 실제 Pop 고용 내역으로 변환한다.
5. `Building.HireWorkers()`가 Province 전체 인구가 아니라 실업 중인 Pop을 선발하도록 변경한다.
6. 건물별 요구 직업과 `JobType`을 연결한다.
7. 급여를 건물 자금에서 차감하고 해당 Pop의 자산에 지급한다.
8. 수익 부족, 건물 축소와 폐쇄에 따른 해고를 구현한다.
9. 특수 건물 인구 배정을 일반 고용과 같은 노동 공급 원장에 통합한다.
10. 건설 회사 노동자를 `nationManhour` 계산에 연결한다.
11. 저장 데이터에 Pop 고용 상태와 건물별 배치 내역을 추가한다.
12. 총인구 보존, 중복 고용 방지, 고용량 제한과 임금 지급 자동 테스트를 추가한다.

## 우선 검증해야 할 규칙

고용 시스템을 연결할 때 최소한 다음 불변 조건을 자동 테스트로 확인해야 한다.

```text
취업자 수 + 실업자 수 ≤ 노동 가능 인구
건물 현재 노동자 수 ≤ 건물 최대 고용량
Province 취업자 합계 = 모든 Pop 취업자 합계
Province 취업자 합계 = 모든 건물 배치 인원 합계
한 사람은 동시에 두 건물에 배정되지 않음
유년기와 비노동 연령 인구는 일반 고용 대상에서 제외
해고된 인원은 다시 실업 인구로 돌아감
```

현재 고용 시스템의 첫 구현 목표는 다음 정도로 제한하는 것이 적절하다.
