## 이번에 연결한 것

건물 노동자 수를 실제 프로빈스 민족집단에 배정하고, 주간 생산 전에 건물 계좌에서 해당 집단 계좌로 임금을 지급한다. 고용과 임금은 다음 순서로 검증했다.

1. 기존 테스트 93개 확인.
2. 고용 테스트 7개를 추가해 미구현 상태의 실패 확인.
3. 고용 구현 후 전체 100개 통과.
4. 임금 테스트 5개를 추가해 미구현 상태의 실패 확인.
5. 임금 구현 후 전체 105개 통과.
6. 소비·산업 지원·건설·연령 이동·오버플로 통합 테스트 추가.
7. 독립 검토에서 발견한 무급 채용 API 우회 경로를 재현하고, 공개 보정 API를 감원 전용으로 제한했다.

최종 검증: **111/111 통과**, 실패·스킵·컴파일 오류 0건. 독립 재검토에서 추가 문제 없음. 에디터 화면의 실제 배치는 별도 플레이 확인이 필요하다.

## 고용 기록

`ProvinceEmployment`가 한 프로빈스의 고용 기록을 소유한다.

```text
프로빈스
  건물 A → 민족집단 1: 25명, 민족집단 2: 75명
  건물 B → 민족집단 1: 10명, 민족집단 2: 30명
```

- `Building.currentWorkers`: 해당 건물의 고용 기록 합계.
- `ProvinceEthnicPop.EmployedPopulation`: 해당 집단이 모든 건물에 취업한 인원 합계.
- `ProvinceEthnicPop.UnemployedPopulation`: 노동가능인구에서 취업자를 뺀 값.
- `Province.hiredPopulation`: 모든 건물의 고용 인원 합계.
- `GetWorkers(building)`: 건물의 민족집단별 인원 읽기 전용 스냅샷.

같은 프로빈스에서만 채용한다. 집단별 노동가능인구와 건물 정원 양쪽을 넘을 수 없다. 계좌 ID 순서와 기존 `ProportionalAllocator`로 정수 나머지를 결정한다.

## 노동가능인구

기존 연령계층 참여율을 유지한다.

| 계층 | 참여율 |
|---|---:|
| 유년기 | 25% |
| 청년기 | 100% |
| 중년기 | 85% |
| 노년기 | 0% |

노동가능인구와 생산성은 다른 개념이다. 이번 구현에서는 참여율을 취업 가능한 인원수 계산에만 사용한다.

초기 건물 인원은 JSON의 `workerScale`로 계산한 수를 실제 민족집단에 배정한다. 총수요가 공급보다 많으면 건물별 수요에 비례하여 줄인다. 초기 고용 배정 자체는 임금을 지급하지 않으며 첫 주간 처리부터 지급한다.

## 주간 채용과 해고

기존 고용을 유지하되 다음 상황에 맞춰 인원을 줄인다.

- 건물 레벨 감소 또는 제거.
- 집단의 노동가능인구 감소.
- 건물이 지급 가능한 임금 예산 부족.

새 인원은 건물당 한 주에 최대 50명까지 채용한다. 노동 공급이 부족하면 건물별 빈자리 수로 나누고, 각 건물의 신규 채용은 집단별 미취업 인원에 비례하여 배분한다.

월간 인구 변동과 연간 연령 이동 직후에는 추가 채용 없이 초과 고용부터 조정한다.

산업 보조금은 관리되는 건물의 노동자 수를 직접 늘리지 않는다. 받은 자금은 다음 주간 채용과 임금 지급의 재원이 된다.

## 임금 설정과 지급

`BuildingType.weeklyWage`는 1인당 주간 임금이다. 기본값은 **1화폐**이며 양수 정수만 허용한다. `Assets/Resources/BuildingTypes.json`의 건물 항목에 설정할 수 있다.

```json
"weeklyWage": 2
```

필드를 생략하면 기본값 1을 사용한다. 현재 임금은 초기 동작 확인을 위한 밸런스 값이다.

| 건물 | 임금으로 사용할 수 있는 금액 |
|---|---|
| 양수 원재료 입력이 있음 | 현재 잔액의 절반, 정수 내림 |
| 양수 원재료 입력이 없음 | 현재 잔액 전부 |

채용 가능 인원은 `임금 예산 / 1인당 임금`을 넘지 않는다. 원재료용 잔액을 남겨도 실제 원재료 재고 부족이나 생산 단위 제한으로 생산하지 못할 수 있다. 수익 기반 임금 협상·자동 밸런싱은 구현하지 않았다.

임금은 프로빈스 내 모든 건물과 근로 집단을 하나의 원장 batch로 정산한다.

```text
건물 계좌 -150
민족집단 A +38
민족집단 B +112
합계         0
```

임금에는 판매세를 부과하지 않는다. 근로 집단이 그 돈으로 시장 상품을 구매할 때 기존 판매세가 적용된다.

`TryProcessWeek(week)`는 같은 주를 다시 호출해도 이중 지급하지 않는다. 과거 주는 거부한다. 교차 원장·잘못된 임금·오버플로·원장 batch 실패 시 해당 프로빈스의 돈과 고용 계획 모두 반영하지 않는다. 게임은 오류를 Console에 기록하고 해당 프로빈스의 그 주 생산과 건설 진행을 건너뛴다.

## 생산과 건설

주간 처리 순서는 고용 계획 및 임금 지급 → 건설회사 공사 → 상품 생산 → 시장 이동 → 소비다.

건설회사의 인시는 기존 기준 인시에 `고용 인원 / 전체 정원`을 곱한다. 고용 인원이 0이면 공사 진행도 0이다. 현재 건설회사 수수료 수입은 없으므로 초기 운영자금이 소진되면 지원금 등 추가 재원이 필요하다.

## 게임에서 확인

이 기능은 별도 작업공간 `D:\ProjectNO\.worktrees\ethnic-employment`에 있다. `market`에 병합하기 전에는 이 폴더를 Unity Hub에서 열어 확인한다.

- 프로빈스 상세 인구 목록: `Labor`, `Employed`, `Unemployed`, `Money`.
- 프로빈스 건물 목록: 레벨과 현재 고용 인원.
- 건설 프로빈스 목록: 전체 인구가 아니라 미취업 노동가능인구 표시.
- 건설 대기열: 고용 비율에 따른 실제 공사 진행.
- 화폐 총량: 임금 지급 전후 동일. 정책 발행이나 통화권 편입 등 별도 변동은 구분해야 한다.

## 경계와 후속 작업

- 문화별 채용 차별, 숙련도, 직업 분류, 프로빈스 간 통근은 아직 없다.
- 미지급 임금 부채 대신 지급 가능한 인원으로 제한한다.
- 주거용 특수 건물의 기존 인구 배치는 유지한다. 특수 건물의 `currentWorkers`는 이번 일반 건물 고용 기록에 포함하지 않는다.
- 고용 기록과 마지막 임금 지급 주차는 저장 형식에 포함되지 않는다. 기존 경제 저장 형식 확장과 함께 다뤄야 한다.
- 임금, 원재료 예산 비율, 주간 채용 상한과 건설회사 수수료는 플레이 밸런스 조정 대상이다.
- 고용 초기화 전 독립 도메인 객체의 기존 인원 설정은 호환되지만, 게임 초기화 후 관리되는 건물의 인원은 직접 수정할 수 없다.
