## 1. 이번 작업의 목적

기존 경제 코드에는 인구의 재산, 시장 재고, 국가 예산과 생산이 존재했지만 화폐가 어디에서 생기고 어디로 이동하는지 하나의 규칙으로 묶여 있지 않았다. 일부 흐름은 값을 직접 더하거나 빼고, GDP 계산이 세금 수입을 만드는 등 실제 거래 없이 돈이 증가할 가능성이 있었다.

이번 작업의 핵심 목표는 다음과 같다.

1. 게임 시작 시 국가와 인구집단이 역사적 조건에 따라 서로 다른 초기 자산을 가진다.
2. 일반적인 경제 활동에서는 돈이 새로 생기거나 사라지지 않는다.
3. 소비자가 상품을 사면 소비자의 돈이 생산자와 국가 세금으로 이동한다.
4. 건물이 원재료를 사용하려면 시장에서 실제로 구매해야 한다.
5. 건설에 들어가는 초기 운영자금은 건물을 발주한 투자자가 낸다.
6. 국가가 명시적으로 화폐를 발행하거나 소각할 때만 총화폐량이 변한다.
7. 잘못된 데이터나 거래는 일부만 적용되지 않고 전체가 취소된다.

핵심 원칙은 다음 한 줄로 요약할 수 있다.

```text
일반 거래: 한 계좌의 감소량 = 다른 계좌들의 증가량
```

상품 생산은 재고를 만들 뿐 화폐를 만들지 않는다. GDP는 통계일 뿐 세금을 자동 생성하지 않는다.

## 2. 전체 구조

```text
JSON 초기 경제 데이터
  ↓
EconomicInitializer
  ↓
국가 또는 중립 프로빈스 MoneyLedger
  ├─ 국가/지역 금고 계좌
  ├─ 인구집단 계좌
  ├─ 건물 계좌
  └─ 진행 중 건설 위임 에스크로 계좌
        ↓
생산자 소유 재고 → 시장 정산 → 소비자 지출
        ↓                 ├─ 생산자 수입
        ↓                 └─ 국가 판매세
건물 생산 ← 원재료 유상 구매
```

구현의 중심은 `MoneyAccount`와 `MoneyLedger`다. 인구, 건물, 국가, 건설 에스크로가 각자 계좌를 가지고 모든 화폐 이동은 원장을 통과한다.

## 3. 핵심 화폐 객체

### 3.1 `MoneyAccount`

파일: `Assets/Scripts/Class/MoneyAccount.cs`

`MoneyAccount`는 경제 주체 한 명 또는 한 객체의 잔액을 보관한다.

- 계좌마다 안정적인 `AccountId`가 있다.
- 잔액은 정수형 `long`을 사용한다.
- 외부 게임 코드에서 잔액을 직접 대입할 수 없다.
- 실제 잔액 변경 함수인 `ApplyDelta()`는 `MoneyLedger` 내부에서만 호출된다.
- 산술 오버플로가 발생하면 변경을 거부한다.

기존 필드는 호환성을 위해 읽기 전용 관점으로 유지된다.

| 기존 개념 | 실제 화폐 원천 |
|---|---|
| `Nation.balance` | 국가의 `MoneyAccount.Balance` |
| `ProvinceEthnicPop.property` | 인구집단의 `MoneyAccount.Balance` |
| `Building.balance` | 건물의 `MoneyAccount.Balance` |
| `GovernmentBudget.MoneySupply` | 국가 `MoneyLedger.MoneySupply` |

### 3.2 `MoneyLedger`

파일: `Assets/Scripts/Class/MoneyLedger.cs`

`MoneyLedger`는 한 통화권의 모든 계좌와 총화폐량을 관리한다.

주요 기능은 다음과 같다.

| 함수 | 역할 | 총화폐량 변화 |
|---|---|---:|
| `TryTransfer()` | 두 계좌 사이의 단순 송금 | 없음 |
| `TryTransferBatch()` | 구매자·판매자·세금 등 여러 이동을 한 번에 적용 | 없음 |
| `TryMint()` | 권한을 확인한 뒤 새 화폐 발행 | 증가 |
| `TryBurn()` | 권한을 확인한 뒤 화폐 소각 | 감소 |
| `TryIssueAndTransferBatches()` | 정책 발행과 분배를 하나의 원자적 작업으로 처리 | 발행량만큼 증가 |
| `Audit()` | 등록 계좌 합계와 기록된 총화폐량 비교 | 없음 |
| `BeginWeek()` | 주간 세금 통계 초기화 | 없음 |

원장은 다음 오류를 거래 적용 전에 검사한다.

- 0 이하의 잘못된 거래 금액
- 보내는 계좌의 잔액 부족
- 서로 다른 원장에 속한 계좌 간 거래
- 등록되지 않은 계좌
- 권한 없는 발행과 소각
- 합계가 0이 아닌 불균형 일괄 거래
- 잔액, 총화폐량, 세금, 거래 기록의 `long` 오버플로

검증에 실패하면 잔액, 총화폐량, 거래 기록과 주간 세금 중 어느 것도 변하지 않는다.

### 3.3 원장별 통화권

- 각 국가는 자신의 `MoneyLedger`를 하나 가진다.
- 어느 국가에도 속하지 않은 중립 프로빈스는 임시 `LocalLedger`와 지역 금고를 가진다.
- 국가와 중립 프로빈스 사이의 일반 거래는 허용하지 않는다.
- 환율과 국제 결제는 아직 구현하지 않았다.

## 5. 경제 초기화 순서

파일: `Assets/Scripts/Class/EconomicInitializer.cs`

`GameManager`는 국가, 프로빈스, 인구, 건물과 소유권을 로드한 다음 `EconomicInitializer.Initialize()`를 호출한다.

```text
국가·프로빈스·인구·레시피 JSON 검증
  ↓
프로빈스 소유 국가 확인
  ↓
국가별 원장과 국고 계좌 생성
  ↓
중립 프로빈스별 지역 원장과 지역 금고 생성
  ↓
인구집단 계좌 등록
  ↓
시작 건물 계좌 등록
  ↓
국고/지역 금고 → 시작 건물 운영자금 이전
  ↓
등록 계좌 합계를 초기 MoneySupply로 확정
  ↓
Audit로 합계 검증
```

초기화는 먼저 전체 계획을 검증하고 나서 원장과 잔액을 변경한다. 뒤쪽 레코드에서 오류가 발견되더라도 앞쪽 국가나 인구만 부분 초기화되지 않는다. 오류를 수정한 뒤 다시 초기화할 수 있도록 기존 객체 상태도 유지한다.

초기화가 거부하는 대표적인 경우는 다음과 같다.

- 국가 또는 인구의 음수 초기자금
- 0 이하이거나 유한하지 않은 생활수준
- JSON 레시피의 0 이하 초기 운영자금
- 국가 소유 프로빈스에 작성된 0이 아닌 지역 금고
- 시작 건물 전체를 자본화할 수 없는 국가 또는 지역 금고
- 경제 초기화 대상에서 소유 국가가 빠진 프로빈스
- 초기 운영자금 곱셈이나 합계의 오버플로

오류 메시지에는 JSON 리소스, 레코드와 필드가 포함된다.

## 6. 화폐 보존 법칙

국가 원장의 총화폐량은 다음 계좌들의 합계다.

```text
MoneySupply =
    국가 금고 잔액
  + 국내 인구집단 잔액 합계
  + 국내 건물 잔액 합계
  + 진행 중 건설 에스크로 잔액 합계
```

중립 프로빈스는 국가 금고 대신 지역 금고를 사용하고 해당 프로빈스의 계좌만 포함한다.

일반 송금, 시장 구매, 판매세 징수, 건설 투자와 취소는 계좌 사이에서 돈의 위치만 바꾼다. 다음 두 작업만 총화폐량을 바꾼다.

- `Mint`: 새 화폐를 발행하므로 총화폐량 증가
- `Burn`: 화폐를 소각하므로 총화폐량 감소

개발 빌드와 에디터에서는 매주 마지막에 `AuditEconomyLedgers()`가 모든 원장을 검사한다. 기록된 `MoneySupply`와 실제 등록 계좌 합계가 다르면 오류를 발생시킨다.

## 7. 중립 프로빈스의 국가 편입

파일: `Assets/Scripts/Class/ProvinceCurrencyMigration.cs`

중립 프로빈스는 이미 자체 지역 화폐권으로 경제 활동을 할 수 있으므로 단순히 `Nation.AddProvinces()`만 호출하면 안 된다. `TryAbsorbNeutralProvince()`가 1:1 흡수를 수행한다.

```text
편입 전
중립 원장 = 지역 금고 + 인구 + 건물 + 건설 에스크로

편입
  ├─ 모든 계좌와 시장 재고 소유자 검증
  ├─ 지역 금고 잔액을 국가 금고로 이동
  ├─ 인구·건물·에스크로 계좌를 국가 원장으로 이동
  └─ 시장 재고의 생산자 소유권 유지

편입 후
중립 원장 = 0
국가 원장 공급량 = 기존 국가 공급량 + 기존 중립 공급량
```

편입 전후 두 원장의 합산 화폐량은 같다. 환율 계산이나 발행은 없다.

다음 조건이면 편입 전체를 거부한다.

- 다른 국가 원장에 속한 인구, 건물 또는 에스크로가 존재함
- 시장 재고의 공급자가 외부 통화권 계좌임
- 공급자가 등록되지 않은 계좌임
- 지역 금고가 상품 공급자로 등록되어 있음
- 원장 계좌 구성과 프로빈스 경제 객체가 일치하지 않음

직접 `Nation.AddProvinces()`를 호출해 초기화된 중립 프로빈스를 우회 편입하는 것도 차단했다.

## 8. 건설 투자금과 에스크로

관련 파일:

- `Assets/Scripts/Class/ConstructionMandate.cs`
- `Assets/Scripts/Class/BuildingFactory.cs`
- `Assets/Scripts/UI/Building/BuildProvinceButtonUI.cs`

건설 위임이 생성될 때 투자자는 완공 후 건물이 사용할 운영자금 전액을 미리 낸다. 이 돈은 진행 중에 `ConstructionMandate`의 에스크로 계좌에 보관된다.

### 발주

```text
국가 또는 투자자 계좌
  └─ initialCapital 전액 송금 → 건설 위임 에스크로
```

발주 전에 투자자와 대상 프로빈스가 같은 원장인지, 투자자가 전액을 낼 수 있는지, 건설 자재 예약이 가능한지를 모두 확인한다. 하나라도 실패하면 위임, 자재 예약과 송금이 모두 생성되지 않는다.

### 완공

```text
건설 위임 에스크로
  └─ 전액 송금 → 새 건물 또는 업그레이드된 기존 건물
```

건물 계좌를 원장에 등록하고 에스크로 전액을 이전한다. 업그레이드는 기존 건물 계좌에 운영자금을 더한다. 이후 에스크로 계좌를 원장에서 제거한다.

### 취소

```text
건설 위임 에스크로
  └─ 전액 환불 → 원래 투자자
```

완공과 취소는 각각 한 번만 처리된다. 반복 호출로 돈이 중복 이전되지 않는다.

현재 `initialCapital`에는 다음 비용이 포함되지 않는다.

- 건설회사의 공사 수수료
- 건설 노동자의 임금
- 건설 자재 가격

자재는 기존 예약 시스템을 사용한다. 수수료와 임금은 고용 시스템 단계에서 연결해야 한다.

## 9. 생산자 소유 시장 재고

관련 파일:

- `Assets/Scripts/Class/MarketInventory.cs`
- `Assets/Scripts/Class/Market.cs`
- `Assets/Scripts/Class/Province.cs`

기존 `ProductState.Stock`은 시장 전체 재고만 표시해 실제 판매자가 누구인지 알 수 없었다. 이제 상품별 `ProductInventory`가 공급자 계좌별 재고 lot을 보관한다.

```text
ProductState.Stock = 모든 공급자 lot 수량의 합계
```

생산자 유형은 다음과 같다.

- 건물 생산품: 생산한 `Building` 계좌가 공급자
- 프로빈스 기본 식량: 각 `ProvinceEthnicPop` 계좌가 공급자

기본 식량은 인구수 비율로 각 인구집단의 생산량을 나눈다. 정수 나머지는 안정적인 계좌 ID를 이용한 결정적 비례 배분으로 처리한다. 기본 생산은 상품만 만들며 인구 재산을 직접 증가시키지 않는다.

여러 공급자가 같은 상품을 보유하면 현재 재고 비율에 따라 판매량을 배분한다. 같은 소수점 나머지가 생기면 안정적인 공급자 키 순서로 결정하므로 같은 입력은 항상 같은 결과를 만든다.

품질, 거리, 운송비는 아직 판매자 선택에 반영하지 않는다. 미래에는 공급자 선택 정책만 교체하고 생산자 소유 재고와 정산 구조는 그대로 유지할 수 있다.

## 10. 시장 구매와 정산

파일: `Assets/Scripts/Class/MarketSettlement.cs`

### 단일 상품 구매

`TryPurchase()`는 다음 순서로 처리한다.

1. 요청량을 실제 재고량으로 제한한다.
2. 구매자 잔액과 단가로 구매 가능한 수량을 계산한다.
3. 상품을 어느 공급자에게서 얼마나 살지 계획한다.
4. `gross = 수량 × 단가`를 계산한다.
5. 판매세를 계산한다.
6. 구매자, 모든 판매자와 국고가 포함된 하나의 균형 거래를 만든다.
7. 원장의 `TryTransferBatch()`를 적용한다.
8. 송금에 성공한 뒤에만 공급자 재고와 총재고를 감소시킨다.
9. 실제 구매량만큼 `LastDemand`를 증가시킨다.

정산식은 다음과 같다.

```text
구매자 지출액 = 모든 판매자의 순수입 합계 + 국가 판매세
```

예를 들어 총구매액 100, 판매세 10%, 두 생산자의 판매 비중이 60:40이라면 다음처럼 이동한다.

```text
구매자       -100
국가 금고     +10
생산자 A      +54
생산자 B      +36
합계            0
```

### 묶음 구매

`TryPurchaseBasket()`은 건물 원재료처럼 여러 상품을 한 번에 구매할 때 사용한다.

- 전체 수량이 필요한 경우 `requireFullQuantity: true`를 사용한다.
- 한 상품이라도 재고나 자금이 부족하면 전체 묶음을 취소한다.
- 같은 상품을 두 번 넣은 잘못된 요청도 거부한다.
- 검증이 성공한 뒤 모든 화폐와 재고를 한 번에 반영한다.

따라서 돈만 빠지고 재료를 받지 못하거나, 일부 재료만 사서 완제품을 만드는 상태가 발생하지 않는다.

## 12. 건물의 원재료 구매와 생산

파일: `Assets/Scripts/Class/Province.cs`

건물은 더 이상 무료로 시장 재고를 가져와 생산하지 않는다. 건물 계좌가 원재료를 시장에서 구매하고 공급자에게 대금을 지불한다.

```text
건물 계좌
  └─ 원재료 구매대금 → 원재료 생산자 + 판매세
                         ↓
                     원재료 재고 감소
                         ↓
                     완제품 생산
                         ↓
                     건물 소유 재고 증가
```

생산 가능 규모는 노동력, 건물 자금과 모든 원재료 재고의 최소값으로 제한된다. 양수인 원재료가 하나라도 있는 레시피는 완전한 정수 생산 단위만 허용한다.

예를 들어 완제품 1회를 생산하는 데 철 2개가 필요한데 건물 자금으로 철 1개만 살 수 있다면 철 1개를 사고 일부 완제품을 만드는 것이 아니라 생산 전체를 하지 않는다. 이 규칙은 원재료 수량을 각각 내림 처리해 일부 재료를 생략한 채 결과물을 만들던 오류를 방지한다.

입력이 전혀 없는 레시피는 기존처럼 노동력 비율에 따른 연속 생산 규모를 사용할 수 있다.

생산 과정에서 다음을 먼저 검증한다.

- 완제품 수량을 정수로 안전하게 표현할 수 있는가
- 완제품을 공급자 소유 재고에 추가할 수 있는가
- 필요한 모든 입력을 전량 구매할 수 있는가
- 모든 구매 계좌가 같은 원장에 속하는가

검증 후 원재료 정산에 성공해야만 건물 소유 완제품 재고가 생성된다.

## 13. 판매세와 국가 정책

파일: `Assets/Scripts/Class/GovernmentBudget.cs`

### 판매세

판매세는 `SalesTaxBasisPoints` 정수로 관리한다.

```text
1,000 basis points = 10%
10,000 basis points = 100%
```

세금은 실제 시장 판매가 성공할 때 판매자 몫에서 원천징수되어 국고 계좌로 이동한다. `WeeklyTaxRevenue`는 새 주가 시작될 때 0으로 초기화되고 그 주에 실제로 정산된 세금만 누적한다.

### GDP

GDP와 평균 GDP는 통계로 남지만 GDP 값만으로 국고에 돈을 생성하지 않는다. 기존 GDP 기반 `CollectTaxes()` 경로는 제거됐다.

### 화폐 발행과 정책 분배

`GovernmentBudget.PrintMoney()`는 정책 계획 전체를 먼저 검증한다. 발행이 필요한 정책은 국가 권한으로 정확한 금액을 한 번 발행하고, 같은 원자적 작업 안에서 지원 대상에게 분배한다.

```text
발행 승인 금액 → 국가 국고
                  ├─ 산업 지원 대상 계좌
                  ├─ 부동산 지원 대상 인구 계좌
                  └─ 정책상 국고에 남는 연구·미분배 금액
```

발행한 돈이 국고에도 남고 지원 대상에게도 새로 더해지는 이중 지급을 방지했다. 정책 적용 중 오버플로, 중복 계좌 ID 또는 잘못된 대상이 발견되면 발행, 송금과 정책 효과 전체가 적용되지 않는다.

## 14. 실제 주간 경제 실행 순서

파일: `Assets/Scripts/Manager/GameManager.cs`

현재 `ProcessWeeklyEvents()`의 주요 순서는 다음과 같다.

따라서 현재 구현은 고용 시스템을 붙일 수 있는 화폐·시장 기반을 완성한 상태이며, 고용 자체가 완성된 것은 아니다.

- 원장의 기록된 총화폐량과 거래 기록
- 진행 중 건설 위임의 에스크로 잔액
- 상품별 생산자 소유 재고 lot

따라서 새 시스템을 안전하게 저장하고 불러오는 기능은 아직 완성됐다고 볼 수 없다. 저장 형식을 확장할 때는 계좌, 원장과 재고를 한 번에 복구하고 로드 직후 `Audit()`을 통과하도록 만들어야 한다.

### 고용과 임금

아직 구현하지 않은 항목은 다음과 같다.

- 노동가능인구와 실제 취업자의 연결
- 건물별 채용 인원과 직업 배치
- 건물 계좌에서 노동자 계좌로 지급되는 임금
- 인력 부족에 따른 생산 및 건설 속도 감소
- 수익 부족 건물의 감원 또는 생산 중단
- 실업, 임금과 생활수준의 상호작용

화폐 원장과 유상 시장 거래가 준비됐으므로 임금은 미래에 다음과 같은 보존 거래로 추가할 수 있다.

```text
건물 또는 건설회사 계좌 -임금
노동자 인구집단 계좌     +임금
총화폐량 변화                0
```

### 국제 경제

환율, 외환, 국가 간 무역, 관세, 국가 간 프로빈스 정복과 통화 전환은 아직 범위 밖이다. 현재 서로 다른 `MoneyLedger` 사이의 일반 거래는 안전하게 거부된다.

## 20. 다음 권장 작업 순서

1. 기능 worktree를 Unity에서 실제 플레이로 확인한다.
2. 확인이 끝나면 `feature/monetary-circulation`을 `market`에 병합한다.
3. 고용 시스템에서 노동가능인구를 건물의 고용 수요와 연결한다.
4. 건물과 건설회사가 원장을 통해 인구집단에게 임금을 지급하게 한다.
5. 임금 수입 → 소비 → 생산자 수입 → 재고 재생산의 주간 순환을 통합 테스트한다.
6. 이후 저축, 투자, 민족집단의 자동 건설 투자 조건을 설계한다.
7. 경제 상태를 포함하는 저장/불러오기 형식을 추가한다.

현재 단계의 결론은 다음과 같다.

> 국가, 인구집단, 건물과 건설 투자가 같은 화폐 보존 규칙 아래에서 거래하도록 기반을 통합했다. 상품 구매는 생산자와 국가에 실제 대금을 전달하고, 건물 생산은 자금과 원재료에 의해 제한된다. 다음 핵심 단계는 이 기반 위에 고용과 임금 지급을 연결하는 것이다.
