# 건설 자재 조달과 공사대금

구현 브랜치: `feature/construction-procurement` → `market` 병합 완료 (`db80975`)

작업 트리: `D:/ProjectNO/.worktrees/construction-procurement`

기준: `46469e6`의 고용·임금 시스템에 건설 계약·시장 배치 결제·조달·공정 지급·취소를 연결했다. 2026-09-19 `market` 브랜치에 병합하고 전체 EditMode 테스트를 다시 검증했다.

## 계약과 돈의 구분

발주 시 고정 공사대금(`ConstructionFee`)과 완공 건물의 운영자금(`InitialCapital`)을 함께 예치한다. 자재는 예치금과 별도로 발주자 가용 잔액에서 구매한다. 시장 재고가 없다는 이유만으로 발주를 거부하지 않는다. 레시피 설정은 계약 시 스냅샷으로 보관하므로 발주 후 레시피 변경이 기존 계약의 대금·자재 조건을 바꾸지 않는다.

자재비는 실제 구매 누계이고 공사대금은 공정 증가에 따른 회사 매출이다. 운영자금은 완공 건물 계좌로 넘어간다. 공사 매출을 순이익으로 간주하지 않으며, 회사 임금은 별도 지출이다. 회사가 이번 주에 받은 공사대금은 다음 주 임금에 사용할 수 있다.

필수 자재별 확보량이 착공 확보율(기본 30%, 정수 수량 올림)에 도달해야 시공을 시작한다. 누적 공정은 각 자재의 누적 확보율 중 가장 낮은 값 이하이다. 자재가 없는 레시피의 자재 상한은 100%이다. 소비량은 공정에 따라 증가하고 완공 시 계약 필요량과 정확히 일치한다. 공정 지급 실패 시 공수·소비량도 변경하지 않는다.

## 실제 주간 실행 순서

`GameManager.ProcessWeeklyEvents`의 기존 순서를 유지하며 국가 공사 배정 직후 `ConstructionWeeklySimulation.Process`를 호출한다.

1. 고용·임금 처리와 지급 성공 프로빈스 집합 구성.
2. 시장 주간 통계 초기화, 도로 연결 캐시 갱신, 국가의 대기 공사 재배정.
3. 활성 공사를 수집하고 같은 `Products` 사전을 사용하는 공유 시장마다 조달 배치를 한 번 처리.
4. 임금 지급에 성공한 프로빈스의 건설회사만 한 번 시공.
5. 프로빈스 생산, 국가 시장으로 생산품 이동, 소비와 기존 후속 경제 처리.

따라서 이번 주 생산품은 이번 주 건설 조달 이후에 시장에 들어간다. 다음 주까지 남아 있는 재고가 다음 조달 대상이다. 같은 국가 공유 시장에 연결된 여러 프로빈스의 공사를 따로 구매시켜 재고나 발주자 잔액을 중복 계산하지 않는다. 도로 단절 시 현재 프로빈스 시장을 사용한다.

시장 배치 실패 시 해당 공사의 `ProcurementFailed`를 표시하고 프로젝트 ID를 포함한 오류 로그를 남긴다. 실패한 구매는 확보량·지출을 변경하지 않는다. 다만 임금이 지급되었고 이미 확보한 자재가 있다면 그 한도에서 시공할 수 있다. 재고·자금 부족으로 구매량이 0인 정상 배치는 조달 오류가 아니며 자재 대기로 나타난다. 자재가 필요 없는 계약은 시장 없이도 지급된 노동으로 진행한다.

## 대기열과 툴팁

기존 `BuildQueueItem.countText`에 짧은 상태와 공정률 두 줄을 표시한다. `Wait mats`는 자재 대기, `Buy failed`는 조달 실패, `Queued`는 배정 대기, `Ready`는 시공 준비, `Building`은 진행 중이다. 완공·취소는 `Complete`·`Cancelled`로 표시한다.

행에 마우스를 올리면 기존 `BuildRequirementTooltip`을 통해 전체 상태, 공정률, 자재 공정 상한, 남은 공수, 누적 자재비, 지급 공사대금/계약 총액, 운영자금, 현재 가격 기준 예상 잔여 자재비를 확인한다. 예상 잔여 비용은 앞으로 구매할 수량에 대한 참고값이며, 재고 확보나 미래 가격을 보장하지 않는다. 가격이 누락·유효하지 않거나 계산 범위를 넘으면 0 대신 `Unavailable`로 표시한다.

실제 프리팹의 LiberationSans SDF는 한글 글리프를 제공하지 않으므로 기존 영문 UI와 맞춰 상태·경제 설명도 영어로 작성했다. 신규 씬 참조나 글꼴 자산은 필요 없다. 짧은 상태는 기존 30pt 글꼴과 약 158.14 × 100 px 셀을 사용하고, 긴 금액은 최대 본문 너비 360 px인 툴팁에서 줄바꿈한다.

## 취소와 소유권

완공 건물의 소유자는 발주자이다. 같은 종류의 기존 건물을 증설할 때 소유자가 다르면 거부한다. 취소 시 아직 지급하지 않은 공사대금과 운영자금만 환불한다. 이미 소비한 자재와 지급한 공사대금은 돌려주지 않는다. 미사용 자재는 발주자 소유 판매 재고로 현재 접근 가능한 시장에 반환하고, 실제로 재판매될 때 판매대금이 발생한다. 안전한 반환 시장·원장을 결정할 수 없으면 취소가 실패하며 기존 상태를 유지한다.

## 검증 기록과 Unity 수동 확인

Unity `6000.0.71f1`의 숨김 배치 EditMode 테스트를 사용했다. 2026-09-18 최종 결과는 신규 통합 테스트 7/7 통과, 관련 회귀 묶음 33/33 통과, 전체 EditMode 217/217 통과이며 모두 실패 0개이다. 결과 파일은 작업 트리의 `TestResults/task6-green-final-20260918.xml`, `task6-green-regression-20260918.xml`, `task6-full-final-20260918.xml`이다. 이전 단계의 210개에 실제 주간 서비스와 UI를 검증하는 테스트 7개를 추가했다. 2026-09-19 `market` 병합 후 `TestResults/postmerge-construction-20260919.xml`로 전체 EditMode 테스트를 다시 실행했으며 217/217 통과, 실패 0개, 건너뜀 0개였다.

전체 첫 실행에서는 기존 UI 문자열 기대값과 새 테스트의 전역 레시피 정리 누락으로 2개가 실패했다. 남은 공수 상세 검증을 유지하며 UI 기대값을 갱신하고 새 테스트의 정리를 추가한 뒤 전체를 다시 실행했다. 최종 전체 로그에는 C# 컴파일 오류·경고나 글리프 누락 경고가 없었다. 기존 환경의 라이선스 갱신 진단(`Access token is unavailable; failed to update`)은 남아 있으나 테스트 실행은 완료되었으며 기기 라이선스 설정은 변경하지 않았다.

자동 통합 검증은 초기 자본, 임금, 세금 포함 자재 구매, 공사 지급, 완공까지 각 단계의 원장 총액을 최초 2,000과 비교한다. 공유 시장 중복 입력, 임금 실패, 조달 실패 후 기존 자재 시공, 고립 시장, 미배정 공사, 자재 없는 계약도 검증한다. UI 검증은 실제 `Assets/Prefabs/UI/UI/Build/BuildQueueItem.prefab`을 로드해 모든 상태의 선호 크기가 기존 셀 안에 들어가는지, 기본 글꼴과 폴백에 실제 표시 문자의 글리프가 있는지, 긴 툴팁이 줄바꿈되는지 확인한다.

Play Mode에서 직접 화면을 조작하거나 육안으로 렌더링을 확인한 결과는 아직 없다. 실제 게임 화면에서는 다음을 확인해야 한다.

1. `PlayScene`에서 국가 건설 대기열을 열고 같은 국가 시장에 연결된 두 프로빈스에 공사를 발주한다. 부족 재고가 각 공사에 배분되고 무상 확보·음수 잔액이 없는지 확인한다.
2. 대기열의 상태/공정률이 건물명·프로빈스명과 겹치지 않고 행에 마우스를 올렸을 때 상세 경제 수치가 나타나는지 확인한다. 화면 가장자리와 서로 다른 해상도에서도 툴팁을 확인한다.
3. 자재 부족·임금 실패·정상 조달·완공 전환에서 공정률과 지급액이 일치하는지 확인한다. 조달 실패를 재현할 때는 Console 오류와 `Buy failed`를 함께 확인한다.
4. 일부 공정 후 취소하여 미사용 자재가 발주자 소유 재고로 반환되고, 운영자금/미지급 공사대금만 환불되는지 확인한다.

## 미구현 범위

운송회사와 운송비, 민간 자본가의 자동 투자, 자재비 총액 상한, 자동 추가 투자·대출·자동 취소는 구현하지 않았다. 현재 자재 누적 지출에는 계약상 상한이 없고, UI에서 누적 지출과 예상 잔여 비용을 구분한다. 주민 소비·공장 구매까지 합치는 공통 시장 주문 배분과 소유자별 같은 종류의 복수 건물도 범위 밖이다.
