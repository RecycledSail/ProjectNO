# 국가 공유시장 경매와 가격 형성

> 구현 기준: 2026-09-21
> 구현 브랜치: `feature/market-clearing`
> 설계: `docs/superpowers/specs/2026-09-19-market-clearing-design.md`
> 계획: `docs/superpowers/plans/2026-09-19-market-clearing.md`

## 구현 상태

주민, 일반 공장과 건설 프로젝트의 돈으로 뒷받침된 주문은 기존 국가·지역 시장에서 함께 수집되고 상품별 단일가격 경매로 청산된다. 거래는 같은 `MoneyLedger`의 등록 계좌 사이에서만 이루어지며, 판매세와 판매대금까지 포함한 시장 단위 batch가 사전 검증된 뒤 반영된다.

연결 여부는 새 시장을 만들지 않고 기존 시장 객체의 정체성을 그대로 사용한다.

- 수도와 도로로 연결된 프로빈스: 소속 국가의 `NationMarket`과 국가 원장
- 고립된 프로빈스: 해당 프로빈스의 `ProvinceMarket`과 현재 활성 원장
- 주민, 공장, 건설 모두 `MarketAccess.TryResolve`의 같은 규칙을 사용한다.

## 실제 주간 실행 순서

`GameManager.ProcessWeeklyEvents`와 `WeeklyMarketSimulation.Process`의 현재 실행 순서는 다음과 같다.

1. 주간 번호를 증가시키고 프로빈스별 고용·임금을 일괄 지급한다.
2. 원장의 주간 세금 통계와 기존 상품의 주간 통계를 초기화한다.
3. 도로 연결 캐시를 갱신하고 대기 중인 건설 위임의 회사 배정을 재시도한다.
4. 임금 지급에 성공한 프로빈스가 기본 생산을 수행하고, 공장은 이전 주까지 보유한 원재료만 소비해 생산한다.
5. 연결 프로빈스에서 생산된 lot을 국가 시장으로 이동한다.
6. 주민 식량 주문, 일반 공장 원재료 주문, 건설 자재 주문 순서로 수집하고 구매자별 시작 잔액 안에서 전역 예약 예산을 제한한다.
7. 시장 ID, 상품명과 주문 ID를 안정적인 서수 순서로 정렬한 뒤 상품별 단일가격 계획을 만든다.
8. 수령 계획을 먼저 검증하고, 시장의 화폐·세금·판매자 재고를 한 batch로 정산한다.
9. 주민 소비, 공장 입력 재고와 건설 자재 수령을 확정한 뒤 이번 주 수요·청산가격과 다음 주 기준가격을 확정한다.
10. 임금 지급에 성공한 건설회사가 확보된 자재의 공정 한도 안에서 공사를 진행한다.
11. GDP·물가지수와 화폐정책을 갱신하고 개발 빌드에서 원장을 감사한다.

건설은 이번 주에 생산된 자재를 같은 주 경매에서 받아 같은 주 공사에 사용할 수 있다. 반면 공장이 이번 주 경매에서 받은 원재료는 생산 단계가 이미 끝난 뒤이므로 다음 주부터 사용할 수 있다. 자동 장기 테스트는 1주차 입력 구매 시 완제품 공급 `0`, 2주차 완제품 공급 양수를 확인한다.

## 가격과 수요 필드

| 필드 | 현재 의미 |
|---|---|
| `Price` | 다음 주 주문의 기준가격이자 공통 최소 판매가격. 가격 압력 계산 결과이며 항상 `1` 이상이다. |
| `LastPrice` | `BeginWeek()`가 저장한 이번 주 경매 시작 전 기준가격. |
| `LastClearingPrice` | 이번 주 상품의 실제 단일 청산가격. 거래가 없으면 `LastPrice`를 사용한다. |
| `LastSupply` | 이번 주 새로 들어온 공급량. 보유 재고 전체와 다르다. |
| `LastDemand` | 이번 주 실제 판매·체결 수량. |
| `RequestedDemand` | 현재 기준가격 이상을 지불할 의사가 있고 예약 예산으로 뒷받침된 유효 주문 수량. |
| `UnmetDemand` | `RequestedDemand - LastDemand`, 즉 유효 주문 중 체결되지 못한 수량. |

GDP와 물가지수는 다음 주의 `Price`가 아니라 이번 주 관측가격인 `LastClearingPrice`를 사용한다. 거래가 없는 상품은 `LastPrice`가 관측가격이다.

## 단일가격과 동률 규칙

- 공급이 유효수요 이상이면 모든 유효 주문을 현재 기준가격으로 전량 체결한다.
- 공급이 부족하면 최대입찰가가 높은 주문부터 배정하고 마지막 낙찰 입찰가를 그 상품의 단일 청산가격으로 사용한다.
- 같은 상품의 모든 낙찰자는 자신의 입찰가가 아니라 동일한 청산가격을 지급한다.
- 경계 입찰가가 같은 주문은 주문량에 비례해 배분한다.
- 최소 체결량보다 작은 몫은 제거한 뒤 같은 경계 집합에 재배분한다.
- 정수 나머지는 안정적인 주문 ID의 서수 순서로 배분하므로 입력 열거 순서가 결과를 바꾸지 않는다.
- 공급 lot의 판매자 배분도 기존 결정적 비례 배분을 유지한다.

## 공장 입력 재고와 한 주 시차

일반 공장은 실제 양수 보유량만 `InputInventory`에 저장한다. 생산은 시장 재고를 직접 사지 않고 보유 입력을 모든 레시피 품목에 대해 완전 생산 단위로 차감한다. 입력 하나가 부족하면 가능한 완전 단위까지만 생산하며, 경매에서 일부 품목만 체결돼도 그 품목은 사라지지 않고 다음 주를 위해 남는다. `ConstructionCompanyBuilding`은 일반 공장 원재료 주문에서 제외된다.

## 저장 형식

현재 경제 저장 형식은 버전 `2`다. 버전 2는 다음 신규 상태를 보존한다.

- 공장의 희소 원재료 재고
- 상품의 `RequestedDemand`, `UnmetDemand`, `LastClearingPrice`
- 기존 가격, 공급·판매 통계와 생산자별 재고 lot

버전 `1` 저장은 로드 전 버전 2로 마이그레이션한다.

- 공장 입력 재고: 빈 사전
- `RequestedDemand = LastDemand`
- `UnmetDemand = 0`
- `LastClearingPrice = Price`

구조가 잘못됐거나 지원하지 않는 버전은 분리된 복원 세계를 게시하기 전에 거부한다.

## 자동 검증 증거

Unity 6000.0.71f1에서 2026-09-24 최종 수정에 실행한 결과다. 시간은 기기 의존적인 통과 기준이 아니라 관찰값이다.

| 실행 | 결과 | 측정 |
|---|---|---|
| 최종 수정 집중 fixture | `148/148`, 실패 `0`, 건너뜀 `0`, 미결정 `0` | NUnit `0.412992 s`; stale 정산, 고가격 경계, 설정 전달, 무체결 가격, 실패 장부 정렬 수와 수령 단일 순회 회귀 포함 |
| `MarketLongRunTests` | `1/1`, 실패 `0`, 건너뜀 `0` | NUnit `0.2634798 s`; 정방향 52주와 역방향 52주의 주별 잔액·재고·가격·체결 상태 동일 |
| `MarketClearingPerformanceTests` | `1/1`, 실패 `0`, 건너뜀 `0` | 연결 프로빈스 `200` × 일반 공장 `25`; 실제 공장 수집 주문 `5,000`, 상품 `18`, 정렬 대상 `5,000`, 체결 `1,953`; 수집 `30.608 ms`, 계획 `18.219 ms`, 정산 `19.036 ms`, 합계 `0.013573 ms/order`; NUnit `4.9285621 s` |
| 전체 EditMode 사전 커밋 표본 | `393/393`, 실패 `0`, 건너뜀 `0`, 미결정 `0` | NUnit `6.5795934 s`; 같은 실행의 성능 측정은 수집 `26.352 ms`, 계획 `8.672 ms`, 정산 `7.210 ms`, 합계 `0.008447 ms/order` |
| 커밋된 HEAD 전체 EditMode 표본 | `393/393`, 실패 `0`, 건너뜀 `0`, 미결정 `0` | NUnit `6.3645542 s`; 같은 실행의 성능 측정은 수집 `26.801 ms`, 계획 `8.503 ms`, 정산 `7.052 ms`, 합계 `0.008471 ms/order` |

52주 테스트는 연결 시장과 고립 시장, 5개 인구집단, 두 입력을 쓰는 공장, 두 자재를 쓰는 건설 프로젝트를 포함한다. 매주 원장 감사와 초기 총화폐량, `Price >= 1`, 상품 재고·공장 입력 재고의 비음수를 확인한다. 역방향 열거 실행은 계좌 잔액, 판매자 lot, 상품 가격·수요·체결 통계, 공장 입력, 주민 생활수준과 건설 자재·진행 상태를 주별로 비교한다.

성능 특성 테스트는 손으로 `MarketOrder`를 만드는 대신 200개 연결 프로빈스의 실제 `Building` 5,000개를 경제 초기화해 구매자·공급자 계좌를 국가 원장에 등록하고, 공장 수집기와 국가 시장 접근 정책으로 주문을 만든다. 테스트 준비와 경제 초기화는 측정 밖이며, 시작 예산 구성·시장 접근·공장 주문 수집, 청산 계획, 수령 검증과 batch 정산을 각각 분리해 측정한다. 최종 수정은 수령자마다 모든 체결을 다시 필터링하던 `O(수령자 × 체결)` 준비를 수령자별 단일 그룹화로 바꿔 체결 목록을 정확히 한 번 순회한다.

새 5,000개 주문 표본의 수집·계획·정산 합계는 집중 실행 `67.863 ms`, 사전 커밋 전체 EditMode 실행 `42.234 ms`, 커밋된 HEAD 전체 EditMode 실행 `42.356 ms`였다. 커밋된 HEAD 표본의 정산은 `7.052 ms`였고 세 표본 모두 주문 수집이 가장 큰 구간이었다. 집중 표본은 지향 목표 50ms를 초과하고 두 전체 표본은 그 아래였으므로, 이 수치는 개선을 확인하는 관찰값일 뿐 절대 시간 상한을 CI 통과 조건으로 사용하지 않는다.

커밋된 HEAD 최종 로그에는 C# 컴파일 오류·경고와 처리되지 않은 예외가 없었다. 그보다 앞선 변경 파일 강제 재컴파일 로그에는 기존 `ProduceUI.buildingsCount`의 `CS0414` 경고 한 종류가 두 번 출력됐다. 수동 PlayMode 검증은 수행하지 않았으므로 **미검증**이다.

## 이번 범위 밖

다음 항목은 이번 구현에 포함하지 않았다.

- 상품 품질, 브랜드와 문화 선호
- 거리, 운송비와 운송회사
- 필수품 우선 배급, 가격상한·보조금 같은 정책 우선순위
- 국제무역, 환율과 관세
- 배당
- 민간의 자동 건설 투자와 기업 이익 기반 생산량 최적화
