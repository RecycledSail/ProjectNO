## 점검 기준

이 문서는 2026-08-19 기준 코드, JSON 데이터, `PlayScene` 직렬화 상태와 Git 이력을 바탕으로 현재 건물 건설 시스템의 구현 범위와 미완성 지점을 정리한다.

현재 결론은 다음과 같다.

> 건설 UI와 예약·건설 회사의 데이터 골격은 존재하지만, 예약이 실제 건설 진행과 완공으로 이어지는 핵심 흐름은 아직 연결되지 않았다.

현재 컴파일은 성공하지만 건설 관련 자동 테스트는 없다. 남은 문제 대부분은 컴파일 오류가 아니라 런타임 데이터와 시스템 간 연결 문제이다.

## 현재 플레이어 건설 흐름

```text
BuildUI 열기
  ↓
생산품 선택
  ↓
PRODUCT_TO_BUILDING으로 건물 타입 검색
  ↓
BuildProvinceUI에서 Province 선택
  ↓
Province에 level 0 Building 즉시 등록
  ↓
ConstructionRequest에 BuildingReservation 추가
  ↓
인접 Province의 건설 회사 탐색 및 슬롯 배정 시도
  ↓
ConstructionRequest 기반 대기열 UI 표시
```

`PlayScene`에는 건설 창, 생산품 버튼, Province 선택 버튼, 대기열 프리팹과 주요 클릭 이벤트가 연결되어 있다. 따라서 플레이어가 생산품을 선택하고 건설할 Province를 고르는 UI 경로까지는 구현되어 있다.

Province 버튼을 클릭하면 `BuildProvinceButtonUI.OnClick()`이 다음 작업을 수행한다.

1. 대상 Province에 해당 건물 객체가 없으면 새 `Building`을 만든다.
2. 새 건물을 `province.buildings`에 즉시 넣는다.
3. 국가의 `ConstructionRequest`에 예약을 추가한다.
4. 인접 Province에서 `ConstructionCompanyBuilding`을 찾아 별도 예약을 배정한다.
5. `BuildUI`의 대기열 표시를 갱신한다.

이때 새 건물은 `level = 0`, `manhoursLeft = 0`, `currentWorkers = 0`인 상태로 Province에 들어가며, 이후 이를 완공 상태로 바꾸는 연결 로직은 없다.

## 서로 분리된 두 건설 경로

### 구형 국가 건설 큐

`Nation`은 다음 필드를 가진다.

- `nationManhour`: 한 주에 사용할 수 있는 국가 건설 노동력
- `buildingsInProgress`: 실제 진행 대상으로 설계된 `Queue<Building>`

`GameManager.ProcessWeeklyEvents()`는 매주 `Nation.SimulateWeeklyTurn()`을 호출한다. 국가는 `CalculateManhour()`로 노동력을 계산하고 `ProgressBuild()`로 큐 맨 앞 건물의 `manhoursLeft`를 감소시킨다.

현재 노동력은 `GlobalVariables.minimumNationManHour`, 즉 10으로 고정되어 있다. 건설 회사 노동력을 반영하는 코드는 TODO 상태이다.

이 경로의 핵심 문제는 UI에서 `Nation.AddToBuildQueue()` 호출이 주석 처리되어 있다는 것이다. 따라서 주간 진행 로직은 실행되지만 `buildingsInProgress` 큐에는 건물이 들어오지 않는다.

추가 문제:

- 한 주에 큐의 첫 건물만 처리하며 남은 노동력으로 다음 건물을 처리하지 않는다.
- 사용 노동력 계산에 `building.manhoursLeft + 1`이 들어간다.
- 완공 시 Province Dictionary에 건물 객체를 다시 넣을 뿐 `level++`을 하지 않는다.
- 신규 건설과 기존 건물 증축을 구분하지 않는다.

### 신형 건설 예약 경로

`ConstructionRequest`는 국가별 `List<BuildingReservation>`을 보관한다. 각 예약은 다음 정보를 가진다.

- 건물 타입
- 대상 Province
- 투자자 `IBuildingInvestor`

현재 없는 정보와 동작:

- 수량과 증축 목표 레벨
- 생성 시각과 우선순위
- 대기·배정·진행·완료·취소 상태
- 비용과 건설 자재
- 실제 진행도
- 예약 제거와 완료 처리
- 구형 `buildingsInProgress` 큐로 넘기는 처리

즉 신형 예약 목록은 UI 대기열의 데이터 원본 역할만 하며, 실제 건설 실행기가 아니다.

## 건설 회사 시스템

`ConstructionCompanyBuilding`은 일반 `Building`을 상속하며 회사 레벨만큼 프로젝트 슬롯을 제공한다.

구현된 기능:

- 빈 슬롯 확인
- 예약을 `BuildingInProgress`로 감싸 슬롯에 등록
- 슬롯 번호로 활성 프로젝트 제거

현재 실제 게임에서 작동하지 않는 이유:

1. 초기 Province 데이터에 건설 회사가 없다.
2. `GlobalVariables.LoadProvinces()`는 모든 일반 건물을 `new Building(...)`으로 생성한다.
3. 데이터에 건설 회사를 추가해도 `ConstructionCompanyBuilding` 인스턴스가 되지 않는다.
4. 따라서 `bld is ConstructionCompanyBuilding` 검사가 성공할 생성 경로가 없다.
5. 회사 프로젝트의 진행도를 갱신하거나 `TryFinish()`를 호출하는 코드가 없다.
6. 국가 요청 목록의 예약과 회사에 전달하는 예약이 서로 다른 객체이다.
7. 인접 Province 순회의 내부 루프만 종료하므로 하나의 요청이 여러 회사에 배정될 수 있다.

데이터상의 건설 회사 이름도 `constructionCompany`가 아니라 `construcntionCompany`로 오타가 나 있다.

## 건설 레시피와 상품 데이터

### 레시피 수 부족

일반 건물 타입은 19개지만 `BuildingRecipes.json`에 있는 레시피는 6개뿐이다.

레시피가 없는 건물 타입:

- `Stable`
- `GoldMine`
- `CoalMine`
- `GlassShop`
- `PaperShop`
- `BookShop`
- `PotionShop`
- `WoolField`
- `ClothShop`
- `LeatherShop`
- `SilkField`
- `CatalystShop`
- `construcntionCompany`

### JSON 스키마 불일치

실제 JSON은 다음 필드를 사용한다.

```json
"buildRequirements": [
  { "item": "Wood", "amount": 2000 }
]
```

하지만 `GlobalVariables.LoadBuildingRecipes()`와 `BuildingrecipeData`는 `requireItems`와 `name`을 기대한다.

```text
JSON buildRequirements ↔ C# requireItems
JSON item              ↔ C# name
```

따라서 현재 스키마로는 `data.requireItems`가 null이 되어 레시피 로드 중 예외가 발생할 수 있다. 코드의 리소스 이름은 `Buildingrecipes`이고 실제 파일은 `BuildingRecipes.json`이므로 파일명 대소문자도 통일할 필요가 있다.

### 상품명 불일치

- 건설 레시피는 `Wood`를 요구하지만 상품 목록에는 `Log`만 있다.
- `SwordSmith`는 상품 목록의 `Sword`가 아니라 `Sworrd`를 생산한다.
- 건물 투입품에 쓰인 `Sand`, `Water`, `Herb`, `Hide`가 상품 목록에 없다.

현재는 건설 레시피의 자재를 검사하거나 시장에서 소비하는 코드 자체도 없다.

## UI 상태와 문제점

### 구현된 부분

- 전체 상품 목록 표시
- 상품별 최근 공급과 수요 표시
- 생산품에서 건물 타입으로 역참조
- 소유 Province 목록 표시
- Province 선택으로 건설 예약 생성
- 예약 목록을 건설 대기열 행으로 표시
- 일일 UI 이벤트를 통한 화면 갱신

### 다른 건물 선택 시 이전 타입 유지

`BuildProvinceUI.UpdateBuildProvinceList()`는 이미 생성된 Province 버튼을 재사용하지만 현재 건물 타입을 다시 전달하지 않는다.

예를 들어 Wheat 건설 화면을 먼저 열고 다음에 Log를 선택하면, 제목은 Log로 바뀌어도 기존 Province 버튼 내부의 건물 타입은 Wheat로 남을 수 있다.

### 대기열 진행도 표시 오류

대기열은 `BuildingReservation` 자체가 아니라 `targetProvince.buildings[buildingType]`의 건물 객체를 표시한다. 이 객체의 `manhoursLeft`는 0이므로 새 예약도 처음부터 진행도가 0으로 표시된다.

예약을 완료하거나 제거하는 로직이 없으므로 대기열에서도 계속 남는다. 같은 건물을 여러 번 예약하면 같은 `Building` 객체를 참조하는 중복 행이 만들어질 수 있다.

### 대기열 갱신의 잠재적 무한 반복

기존 UI 행과 현재 예약의 건물이 다르면 `Destroy()` 후 같은 인덱스를 계속 검사한다. Unity의 `Destroy()`는 프레임 끝에 반영되므로 예약 삭제나 순서 변경이 구현되면 반복문이 빠져나오지 못할 가능성이 있다.

### 기타 미완성 부분

- 자동 건설 버튼 기능 없음
- 예약 취소와 우선순위 변경 기능 없음
- 대기열 항목 클릭 기능 TODO
- Province 건물 상세 버튼 기능 TODO
- `BuildProvinceUI.subUIs`가 씬에서 빈 배열
- `BuildProvinceButtonUI`가 등록한 일일 이벤트 리스너를 해제하지 않음
- Province 목록 정리 시 GameObject가 아니라 `Transform`을 `Destroy()`에 전달
- 건물을 생산하지 않는 `Build_demand`, `Sword` 등의 상품을 선택하면 수동 건설 버튼이 조용히 아무 동작도 하지 않을 수 있음

## 생산과 고용 연결 상태

`Building`에는 `HireWorkers()`와 `ProduceItem()`이 있지만 건물 생산을 주간 경제 처리에 연결한 코드는 없다.

`Province.ProduceGoodsWeekly()`는 현재 `BaseProduction()`만 호출하며 `province.buildings`를 순회하지 않는다. 따라서 건물이 완공되었다고 가정해도 건물의 필요 상품, 생산 상품과 노동자가 실제 시장 생산량에 반영되지 않는다.

산업 보조금은 존재하는 건물의 자금을 늘린 뒤 `HireWorkers()`를 호출한다. 그러나 건설 버튼으로 등록된 레벨 0 건물은 최대 고용 인원이 0이고, `previousGain > 0` 조건도 충족하기 어려워 즉시 고용되지 않는다.

## 저장과 불러오기

`SaveManager`의 데이터 형식에는 Province 건물 목록 필드가 있지만 저장 시 해당 목록을 채우지 않는다. 불러오기에서도 건물 목록을 순회하는 본문이 비어 있다.

현재 저장되지 않는 건설 상태:

- 건물 레벨과 노동자
- 국가 건설 예약
- 구형 건설 진행 큐
- 남은 건설 시간
- 건설 회사의 활성 프로젝트

따라서 건설 기능을 연결한 뒤에는 저장 데이터 형식과 복원 순서도 함께 확장해야 한다.

## 재개 권장 순서

1. `ConstructionRequest`와 `buildingsInProgress` 중 하나를 공식 건설 큐로 정하고 중복 모델을 제거하거나 역할을 명확히 분리한다.
2. 예약에 상태, 수량, 목표 레벨, 진행도와 동일한 프로젝트 식별자를 추가한다.
3. 예약 시 level 0 건물을 Province에 즉시 등록하지 않고 완공 시 신규 레벨 1 건물을 등록한다.
4. `BuildingRecipes.json`의 스키마와 상품명을 통일하고 19개 건물의 레시피를 완성한다.
5. 주간 턴에서 자재 확보, 비용 지급, 건설 회사 배정, 노동력 투입, 완공을 하나의 흐름으로 연결한다.
6. 기존 건물 증축 시 `level++`, 신규 건설 시 `level = 1`이 되도록 구분한다.
7. `ConstructionCompanyBuilding`을 실제로 생성하는 팩토리 또는 로더 분기를 추가한다.
8. 대기열 UI가 `Building`이 아니라 건설 프로젝트를 직접 표시하도록 변경한다.
9. 건설 예약, 진행 상태와 완성된 건물을 저장하고 복원한다.
10. 예약 생성부터 완공까지 자동 테스트를 추가한 뒤 건물 생산을 경제 엔진과 연결한다.

## 한 줄 인수인계

현재는 **건설 주문 UI와 건설 회사 배정 골격까지 구현했으며, 다음 작업은 예약을 실제 주간 건설 프로젝트로 전환하는 단일 실행 흐름을 만드는 것**이다.
