# 건설 자재 조달과 공사대금 정산 설계

작성일: 2026-09-09

상태: 구현 완료 및 `market` 병합 완료 (`db80975`)

## 목적과 범위

국가가 발주하고 건설회사가 시공하며, 완공 건물은 발주자가 소유한다. 장기적으로 민족집단의 자본가도 같은 발주자 인터페이스를 사용하지만 이번에는 민간 자동 투자와 운송회사를 구현하지 않는다.

관련 문서: [[건설 위임 시스템 설계]], [[건설 시스템 현황]], [[민족집단 고용과 임금]].

## 확인한 기존 코드

- `market` 브랜치의 `Nation.CanPlaceConstructionMandate`는 필요 자재 전량과 다른 공사의 예약량을 비교한다. 실제 구매나 재고 차감은 아니다.
- 발주 시 `BuildingRecipe.InitialCapital`을 발주자에게서 예치 계좌로 이체하고, 완공 시 전액을 건물 계좌로 보낸다. 이는 운영자금이지 건설회사 매출이 아니다.
- `ConstructionMandate.ApplyManhours`에는 자재 확보에 따른 공정 제한과 공사대금 지급이 없다.
- `MarketSettlement`는 공급자별 판매대금과 세금을 보존하는 실제 구매 기능을 제공한다. 현재 구매 묶음의 구매자는 한 명이다.
- 고용·임금은 `feature/ethnic-employment` 브랜치의 `46469e6`을 기반으로 건설 조달 기능과 함께 `market`에 병합되었다.

## 합의한 기본 방향

1. 자재는 필요량을 한 번에 확보하지 않고 시장에서 단계적으로 구매한다.
2. 착공 판단은 재료별 확보 비율을 사용한다. 여러 재료의 총수량 평균을 사용하지 않는다.
3. 같은 국가 공유 시장을 이용하는 공사들을 함께 배분한다. 프로빈스별로 같은 재고를 중복 배분하지 않는다.
4. 건설회사 공사대금과 완공 후 건물 운영자금은 분리한다.
5. 구매와 지급은 기존 화폐 원장의 이체로 처리한다. 자동 발행이나 음수 잔고로 부족액을 충당하지 않는다.

## 구현을 위한 구체적인 제안

아래 수치와 취소 규칙은 이번 문서에서 구체화한 제안이다.

### 계약과 예산

- 레시피에 조정 가능한 착공 확보율을 두고 기본값은 30%로 한다.
- 레시피에 고정 공사대금을 별도로 둔다. 운영자금에서 임의로 비율을 떼어 공사대금으로 사용하지 않는다.
- 발주 시 고정 공사대금과 운영자금을 예치한다. 자재비는 그 예치금과 분리된 발주자의 가용 잔액에서 실제 구매 시 지급한다.
- 자재 가격이 오르면 구매 가능한 수량만 줄어든다. 가용 자금이 없으면 추가 구매와 자재를 초과하는 공정을 멈춘다.
- 이번에는 자재 총예산 상한, 자동 추가 투자, 대출, 자동 취소를 도입하지 않는다. 이 방식에서는 자재 누적 지출의 계약상 상한이 없으므로 UI에 누적 자재비와 현재 예상 잔여 자재비를 구분해 표시한다.

### 시장 배분과 구매

- 재고 부족은 발주 거부 사유가 아니라 자재 대기 사유로 처리한다. 단, 발주자가 공사대금과 운영자금을 예치할 돈은 있어야 한다.
- 한 주의 조달 단계에서 같은 시장의 활성 공사 요청을 모두 모은다. 시장 연결 판단은 기존 국가 시장/고립 지역 시장 규칙을 따른다.
- 동일 발주자의 여러 공사는 하나의 잔액을 공유하므로 먼저 공사별 구매 예산을 배분한다. 같은 잔액을 공사마다 전액 사용 가능하다고 계산하지 않는다.
- 예산 내 구매 가능한 요청량을 만들고, 품목별 부족 재고는 요청량에 비례하여 배분한다. 정수 나머지는 안정적인 프로젝트 ID 순서로 처리한다. 이는 완벽한 순번 독립성이나 장기간의 완전한 형평성을 보장한다는 의미는 아니다.
- 배분과 결제 사이에 다른 구매가 끼어들지 않는 단일 조달 단계를 사용한다. 모든 잔액·공급자·재고·오버플로를 사전 검증하고 시장별 배치를 원자적으로 확정한다.
- 구매 성공량만 시장에서 차감하여 프로젝트 보유량으로 옮긴다. 단순 예약 수량을 구매한 것으로 간주하지 않는다.
- 이번 공정성 범위는 건설 프로젝트 사이이다. 주민 소비와 공장 구매까지 공통 배분하는 시장 주문 시스템은 제외한다.

### 착공과 공정

- 모든 필수 자재가 각각 필요량의 30% 이상 실제 확보되면 착공할 수 있다. 정수 필요량에는 올림을 적용한다.
- 누적 공정 상한은 `min(품목별 누적 확보량 / 해당 품목 필요량)`이다. 필요한 자재가 없으면 자재 상한은 100%이다.
- 실제 공정은 자재 상한과 고용·임금 시스템이 제공하는 공수 모두를 만족해야 한다.
- 자재는 공정에 따라 소비된 수량과 미사용 보유량을 구분한다. 완공 시 레시피 필요량이 정확히 소비되어야 한다.
- 공정이 증가한 만큼 고정 공사대금을 회사에 지급한다. 정수 단위 누적 지급액을 계산하여 마지막 지급에서 반올림 잔액을 정산한다.
- 지급 실패 시 공정과 자재 소비도 변경하지 않는다. 회사의 매출은 순이익이 아니며 임금 등 지출은 별도이다.
- 기존 주간 임금 지급이 시공보다 먼저 발생하므로 이번 주 매출은 다음 주 임금에 사용할 수 있다. 새 건설회사는 발주자가 제공한 운영자금으로 최초 임금을 충당한다.

### 소유권·완공·취소

- 완공 건물에 발주자 소유 정보를 기록한다. 같은 종류 건물을 한 프로빈스에 하나로 합치는 현재 구조에서는 소유자가 다른 건물의 증설을 거부한다. 소유자별 복수 건물 구조는 이번 범위가 아니다.
- 완공 시 운영자금만 건물 계좌로 이체한다. 회사가 이미 받은 공사대금은 다시 지급하지 않는다.
- 취소 시 아직 지급하지 않은 공사대금과 운영자금을 발주자에게 환불한다. 이미 지급한 공사대금과 소비한 자재는 돌려주지 않는다.
- 구매했으나 미사용인 자재는 발주자 소유의 판매 재고로 해당 시장에 반환한다. 구매가와 같은 현금 환불을 만들어내지 않는다. 실제로 다시 팔릴 때 판매대금이 발생한다.
- 반환할 시장·원장을 안전하게 결정할 수 없으면 취소를 실패시키고 기존 상태를 유지한다.
- 프로젝트 예치 계좌는 활성 계좌 추적과 통화 이전 검사에 포함하며 잔액이 0일 때만 해제한다.

## 변경 경계

- `BuildingRecipe` 및 로더: 공사대금, 착공 확보율 설정.
- `ConstructionMandate`: 계약 스냅샷, 자재 확보·소비, 누적 지급, 소유권, 완공·취소 처리.
- 신규 조달 서비스: 시장 단위 요청 수집과 예산·재고 배분.
- `MarketSettlement`: 다중 구매자 배치의 사전 검증과 원자적 결제.
- `Nation`: 기존 전량 예약 검사 제거, 예치 및 대기 흐름 연결.
- `GameManager`: 주간 조달 단계와 기존 임금·시공 실행 순서 연결.
- 건설 UI: 자재 대기, 공정 제한, 지급액과 운영자금 구분.

## 검증 기준

- 같은 국가 시장을 사용하는 서로 다른 프로빈스의 동시 공사가 재고를 초과 구매하지 않는다.
- 요청 순서를 뒤집어도 비례 배분 결과가 같으며 정수 나머지 규칙이 일정하다.
- 같은 발주자의 여러 공사가 잔액을 중복 지출하지 않는다.
- 특정 자재만 부족하면 다른 자재가 많아도 조기 착공하거나 공정 상한을 넘지 않는다.
- 가격 급등·무재고·잔액 부족 시 음수 잔액이나 무상 구매 없이 대기한다.
- 공정 지급 실패, 취소 실패, 오버플로 시 부분 상태 변경이 없다.
- 완공·취소를 반복 호출해도 중복 지급·환불·증설이 없다.
- 취소한 미사용 자재의 공급자 소유권과 수량이 보존된다.
- 발주·조달·임금·시공·완공·취소 전후 원장의 총화폐량이 같다.
- 기존 EditMode 테스트와 새 회귀 테스트를 실행하고 실제 결과를 기록한다. 문서 작성만으로 검증 완료를 주장하지 않는다.
